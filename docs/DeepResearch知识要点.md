#### 001 技术栈（A · 开场）✅定稿
- 【一句话】：LangGraph 管控制流、百炼 MCP 管搜索、OpenAI 兼容管模型可插拔；用学习曲线和解析复杂度，换控制流自由＋零搜索运维＋改环境变量切模型。
- 【四格】：
  - 问题：启动需定三件事——①编排框架要支持多步流水线／并行扇出／条件循环；②搜索后端要可靠中文搜索；③LLM 层要兼容企业已有的多模型端点
  - 选型：LangGraph（StateGraph 条件边 + Send 扇出 + reducer 状态合并，并行输出自动合并、无需手动加锁）；阿里百炼 MCP（dashscope `Application.call` 封装搜索，阿里云生态已有访问权限）；OpenAI 兼容协议（改环境变量即切模型）
  - 放弃项：LangChain AgentExecutor（不支持 Fan-out＋条件循环组合）；CrewAI/AutoGen（2025-07 版本不稳、API 频变）；直连 SerpAPI/Bing（需采购配额、中文搜索差）；自建 SearXNG／代理（运维成本）
  - 取舍：用 LangGraph 概念多（StateGraph／Send／interrupt）的学习曲线 + MCP 响应格式不稳定的解析成本，换灵活控制流、零搜索运维与模型可插拔；风险缓解＝版本锁 `langgraph>=0.2.6` + ADR-002 令牌桶 + ADR-010 防御性解析（原文无满意度／收益百分比，勿编）

#### 002 HITL + 速率限制（A · 证据点缀）✅定稿
- 【一句话】：计划后停下等确认、搜索前过令牌桶；多等 10-30 秒、排队 0.4 秒，换相关性提升和 429 从 30% 压到 5% 以下（口述只带 30%→5% 一组数）。
- 【四格】：
  - 问题：宽泛需求直出报告不符预期（Plan 质量不可控）＋ Fan-out 5 并发搜索触发百炼 MCP 429、错误率约 30%
  - 选型：generate_plan 后暂停等用户确认（关键词快速通道＋LLM 意图识别 PlanReflection 双判定）＋令牌桶速率限制器（默认 12 QPS，acquire/aacquire 双模，全局单例排队）
  - 放弃项：无 HITL 直接生成（满意度低＋返工浪费 API 配额）；无速率限制仅靠重试（429 约 30%，仅重试不可靠）
  - 取舍：用 +10-30s 用户等待＋1 次 Plan LLM 调用，换报告相关性显著提升（原文无满意度百分比，勿编）；用 5 条搜索排队约 +0.4s，换 429 错误率约 30%→5% 以下

#### 003 Sub-Graph 多 Agent（S · ⭐主打）已修·取舍⏳
- 【一句话】：单体难测难维护 → 三子图独立编译＋条件边串联；硬数字 OverallState 字段 8→23。
- 【四格】：
  - 问题：单体 StateGraph 超 400 行、难以维护和测试、每次必须跑全图，报告写作只有一次 final_answer 质量不可控
  - 选型：拆为三个独立子图（MainGraph 负责 Plan 确认＋子图调度／ResearchAgent 封装搜索→评估→补搜循环／WriterAgent 封装提纲→写作→审稿→修订循环＋Debate Loop），独立编译、主图条件边串联
  - 放弃项：单体图＋增加节点（测试困难、代码膨胀不可避免）；微服务拆分（过度工程化、增加网络延迟）
  - 取舍：换来各子图独立调试与质量可控（⏳措辞待 Day2 graph 精读对 ADR-003 原文确认）；付出＝子图状态传递过度依赖 OverallState 字段（8→23），需多处同步

#### 005 LLM-as-Judge（S · ⭐主打）✅定稿
- 【一句话】：报告质量不可度量 → E2E 5 维＋组件 7 维独立框架；单次完整评估 10+ 次 LLM 调用，只用于回归/重大变更。
- 【四格】：
  - 问题：传统测试仅能验证功能和代码，无法度量报告是否存在幻觉、信息是否可靠、引用来源真实性、各 Agent 节点输出质量
  - 选型：构建独立的 LLM-as-Judge 评估框架，端到端（5 维度×1-5 分：事实准确性/信息覆盖度/逻辑结构/时效性/引用质量＋幻觉检测）＋ 组件级（7 维度：Plan/Query/摘要保真度/Critic/引用审计/Plan-Query 对齐/Plan Reflection）两层评估
  - 放弃项：人工评估（不可规模化）；规则匹配（无法评估语义质量）；集成进 Agent 代码（增加耦合）
  - 取舍：增加了 LLM 调用，换可量化追踪、可历史对比、组件级定位；仅回归测试与重大变更时触发

#### 004 + 012 检索链（S · ⭐主打，与 004 成链）已修
- 【一句话】：Milvus 存事实 + 双开关精排、召回宁多勿滥；精排比 LLM 逐条打分快 10-50 倍、成本低一个数量级，limit=max(top_k*3,20)。
- 【四格】：
  - 问题：需用向量库实现历史事实语义检索＋跨请求缓存（004）；KB 检索只是语义相近、无法保证最相关，Web 搜索可能含无关/低质结果，伤报告质量（012）
  - 选型：Milvus 存研究事实、Redis 仅作搜索缓存后端（004）；DashScope `gte-rerank` KB/Web 双独立开关精排、召回扩展 `limit = max(top_k*3, 20)`、`rerank()` 永不抛异常只降级（012）
  - 放弃项：ChromaDB（特性不成熟）／云服务（数据需出域）／纯 Redis 向量检索（大批量性能差）（004）；本地模型（dashscope 已兼容、统一认证，免新依赖）／LLM 逐条打分（N 次调用，慢 10-50 倍、成本高一个数量级）（012）
  - 取舍：增加 Milvus/Redis 两套基础设施与一次精排 API 调用、精排后 top_k 减少丢边缘信息，换更贴事实、降低部署成本、缓存命中率提升与搜索 API 调用量下降

## 3. 架构设计：多 Agent 拆分与协作（主挂 ADR-003）

- 三个子图职责：主图只管 Plan 确认与调度 / ResearchAgent 封装「搜索→评估→补搜」循环 / WriterAgent 封装「提纲→草稿→Critic→修订」循环
- 协作方式：子图各自独立编译，主图条件边串联；状态经 `OverallState` 传递（字段 8 → 23，来源 ADR-003）
- Debate Loop 退出条件：`ready_for_polish=True` 或 `revision_count >= 3`；Critic 评分 <6 自动修订（来源 ADR-003）
- README 自述四节点：generate_search / web_search / critique / final_answer

## 4. 知识库：选型 / 设计 / 验证（主挂 ADR-004 + 009 + 012）

- 选型：Milvus 自托管（数据不出域、Dynamic Field 免 migration、IVF_FLAT 适配 10 万级事实量级）；**Redis 只做搜索缓存，不做向量检索**（纯 Redis 不支持向量检索，来源 ADR-004）
- 缓存降级：Redis 不可用 → 进程内内存缓存，业务无感（来源 ADR-004）
- 生命周期四档：off / inform / freshness（默认）/ lifecycle；敏感度阈值 7 / 30 / 180 天；衰减公式 `decay = max(0.3, 1 - age/(2·max_age))`（来源 ADR-009）
- 精排：DashScope `gte-rerank`，KB 与 Web 双独立开关，召回扩展 `limit = max(top_k*3, 20)`，`rerank()` 永不抛异常只降级（来源 ADR-012）
- 验证：见第 5 节（LLM-as-Judge 组件级 + 分层测试）

## 5. 质量与上线标准（主挂 ADR-005 + 011）

- 分层测试：Unit ~120 <5s ／ Integration ~90 <15s ／ E2E ~4 5-10min；214 个测试 <20s（来源 ADR-011）
- Mock 边界：LLM／MCP／Milvus／Embedding 四类隔离；**Redis 用真实本地实例不 mock**（来源 ADR-011）
- LLM-as-Judge：E2E 5 维度 × 1-5 分 ＋ 组件级 7 维度；单次完整评估 10+ 次 LLM 调用，只用于回归与重大变更（来源 ADR-005）
